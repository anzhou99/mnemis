# 让 Agent 审视自己：从零实现自主规划与自我演进

> **Mnemis 系列 · 第 6 篇**
> 前五篇我们给 Agent 装上了手脚、知识库、记忆和团队。这一篇解决最后一个根本问题：Agent 如何知道自己做得好不好？如何从失败中学习？如何在没有人告诉它的情况下，主动变得更好？

---

## 写在前面：从「执行者」到「思考者」

P1 到 P4 构建的 Agent 是一个精良的执行者——你告诉它做什么，它做得很好。但它有一个根本限制：所有的能力都是由我们手动设计和硬编码的。它不会主动发现自己哪里做得不好，也不会根据积累的经验改变自己的行为方式。

P5 要解决这个问题。具体来说，四件事：

一是**长视野任务规划**——面对一个模糊的高层目标，能自主制定多步执行计划，并在执行中途遇到问题时动态调整，而不是崩溃或卡住。

二是**自我反思**——执行完一个任务步骤后，主动评估「做得好不好」，从失败中提炼可以复用的经验，写入长期记忆。

三是**Eval 评估体系**——建立可量化的测试框架，让改进有数字依据而不是主观感受。

四是**Prompt 自动优化**——拿着 Eval 的失败用例，自动分析问题，生成改进版本，通过 A/B 测试验证效果。

这四件事串联起来，构成一个完整的自我改进闭环：执行 → 评估 → 反思 → 优化 → 再执行。

## 一、长视野规划：预先规划 vs 边执行边规划

处理复杂任务有两种截然不同的思路，选择哪种决定了整个系统的架构。

**ReAct（边执行边规划）**：每一步执行完后，根据观察结果决定下一步。这是 P1 实现的模式，灵活但缺乏全局视野——Agent 很容易在某个步骤里陷入局部循环，看不到整体目标。

**ReWOO（预先规划后执行）**：先一次性制定完整计划，包括步骤间的依赖关系和可并行的部分，再按计划执行。这来自 2023 年的一篇论文，核心洞见是：绝大多数任务的步骤在开始时就是可以确定的，不需要看到每一步的结果才知道下一步是什么。

两者的效率差距在有多步工具调用的场景下非常显著：ReAct 需要 N 次「思考 + 等待」的循环，ReWOO 只需要一次规划调用加上并行执行。

我选择了综合方案：**用 ReWOO 做高层规划，保留 ReAct 处理单步内部的意外**。规划器一次性生成带依赖关系的步骤 DAG，执行器按依赖顺序执行，遇到步骤失败时触发动态重规划。

目标分解里有一个细节被很多实现忽视——**里程碑（Milestone）的重要性**。每个步骤必须有一个可被客观验证的完成标准：

```python
@dataclass
class PlanStep:
    description: str   # 这步要做什么
    milestone: str     # 完成时的可验证标准 ← 这个字段很关键
    depends_on: list[str]
```

没有里程碑的步骤，Agent 不知道何时算完成，容易在某个步骤里无限挖深，或者草草了事就宣布完成。好的里程碑应该是具体可验证的（「生成包含5个以上技术点的对比表格」），不是模糊的（「完成研究」）。

动态重规划的触发逻辑也需要仔细设计。我区分了三种失败类型：

```python
# 工具失败：换参数重试即可
# 规划失败：重新思考这步的做法
# 理解失败：回到上层，重新理解目标，触发重规划
```

「理解失败」是最严重的——意味着 Agent 对任务的理解从一开始就有偏差，简单重试没有意义，必须重新规划。识别失败类型是自我改进系统里最关键的能力之一。

## 二、自我反思：三个层次，不只是「检查一下」

执行完一个步骤后，Agent 通常直接继续下一步。P5 在中间插入了一个关键环节：停下来评估。

但反思不只是「检查一下结果」，它有三个层次：

**结果评估**：做到了吗？输出是否达到里程碑的要求？这一层是实时的，评分低于阈值就触发重试。

**过程回顾**：做对了吗？用了哪些工具？顺序合理吗？有没有遗漏的信息？这一层是短时的，结果用来改进当前计划的后续步骤。

**策略更新**：下次怎么做？这类任务的最佳做法是什么？有哪条可以推广到其他类似任务的经验？这一层是长期的，提炼出的经验写入 P3 的语义记忆系统，影响未来的任务执行。

实现上用 LLM-as-Critic 模式：用另一次 LLM 调用评估当前步骤的输出质量，返回结构化的评估结果：

```python
# SelfCritic 的输出结构
{
  "score": 7.5,                    # 1-10 质量评分
  "milestone_met": true,           # 是否达到里程碑
  "failure_type": null,            # tool/planning/understanding/null
  "weaknesses": ["..."],           # 具体不足
  "reusable_insight": "在做搜索类任务时，先确认搜索词的精确性能显著提升结果质量"
}
```

`reusable_insight` 字段是整个反思系统最有价值的输出——这是可以被提炼成通用经验的洞察。系统把它写入 P3 的 `SemanticMemory`，下次执行类似任务时，这条经验会通过记忆检索被注入 system prompt。

**经验是会积累的**。每次执行、每次失败、每次成功，都向记忆系统贡献一条新的经验。随着时间推移，Agent 会越来越擅长它经常执行的任务类型——这是一种轻量级的「从经验中学习」，不需要重新训练模型。

一个容易踩到的坑：**同一个模型评估自己的输出，会产生「自我合理化」**——用同样有问题的推理方式给自己的错误输出打高分。我在实践中用了三种方式缓解：对有明确标准的指标（字数、格式、是否包含代码示例）用规则评分；主观质量用 LLM 评分但用更严格的评分标准；高风险任务考虑用不同的模型交叉评估。

## 三、Eval：你无法改进你无法测量的东西

这句话在软件工程里是老生常谈，在 AI 系统里更是如此——而且往往被忽视。

Eval 不是「测试代码有没有 bug」，而是「量化 Agent 行为的质量」。这两件事有根本的不同：

```
软件测试：assert add(1, 2) == 3  → 对或错，没有中间状态
Agent Eval：「这个回答好不好？」→ 只有「更好」或「更差」，需要评分
```

我为 Mnemis 设计了 20 个测试用例，覆盖五个核心能力维度：工具调用准确性、回答质量、事实准确性、指令遵循度、拒绝幻觉能力。每个用例包含输入、期望行为描述、评分维度，部分用例有参考答案。

评分用 **LLM-as-Judge** 模式——用另一个 LLM 调用对 Agent 的实际输出打分。这种方式对主观质量的评估比规则方式更接近人类判断，代价是引入了评分本身的随机性和偏差：

```python
JUDGE_PROMPT = """评估以下 AI Agent 的回答...
输出 JSON：
{
  "scores": {"answer_quality": 8, "factual_accuracy": 7},
  "overall_score": 7.5,
  "passed": true,
  "reasoning": "回答涵盖了核心概念，但缺少具体示例..."
}"""
```

Eval 结果持久化到 SQLite，支持历史趋势对比：每次运行都是一条记录，可以看到系统随时间的进步或退步。

**最重要的原则，也是最容易被忽视的：测试集永远不能用于调优。**

你建了 20 个测试用例，然后针对这 20 个用例调整 system prompt，直到每个都得高分——你拿到了 95% 的通过率，但 Agent 只是「记住了考题的答案」，真实能力可能没有任何改善。

正确做法是严格区分两组用例：测试集（固定不动，只用来衡量真实能力）和开发集（用于调试和改进）。每次修改 Agent 后，先在开发集上验证，确认有改进再跑测试集。测试集的分数只用来衡量「真实能力」，绝对不用来指导单次调优。

## 四、Prompt 自动优化：DSPy 思想的轻量实现

Stanford 的 DSPy 框架提出了一个革命性的视角：把 Prompt 当作模型参数来优化，而不是手动调整。完整的 DSPy 实现涉及复杂的编译器和优化算法，但它的核心思想可以用简单的方式实现：

```
明确评估标准 → 收集失败案例 → 自动分析问题 → 生成改进建议 → 验证改进效果 → 版本管理
```

我实现了一个 `PromptOptimizer`，它做四件事：

**失败分析**：把 Eval 的失败用例发给 LLM，让它找出失败用例之间的共同规律，定位到 System Prompt 里对应的具体问题。这比逐条人工分析高效得多，而且能发现不明显的模式。

**候选 Prompt 生成**：基于分析结果，让 LLM 直接起草改进版本的 System Prompt。生成的 Prompt 可能不完美，但它提供了一个人工审查的起点。

**A/B 测试**：用相同的测试用例对比新旧 Prompt 的得分。关键细节：A/B 测试用的是开发集，不是测试集，避免测试集被间接用于调优。

**版本管理**：每次修改都创建新版本，永远不覆盖历史。支持回滚到任意历史版本：

```python
# 版本历史示例
v1: [N/A] 初始版本（待优化）
v2: [6.82] 自动优化：工具选择规则不明确
v3: [7.41] 自动优化：引用规范不清晰  ← 活跃
```

版本管理在 Prompt 工程里经常被忽视。你在某个凌晨把 Prompt 改得「感觉更好了」，但两周后发现新问题，想回到上一个版本——如果没有版本管理，你找不到它。

有一个边界需要清楚认识：**不是所有问题都能通过 Prompt 改进**。模型不知道的训练截止后的知识，只能靠 RAG 或搜索补充；模型对复杂推理的能力边界，需要换更强的模型；搜索工具的质量问题，需要改工具实现。在优化之前，先判断「这是 Prompt 问题还是能力边界问题」，是比优化本身更关键的技能。

## 五、演进循环：把四个能力串联起来

单独看，规划、反思、Eval、Prompt 优化各自都有价值。把它们串联成一个自动运行的闭环，才是 P5 真正要做的事。

演进循环的触发有两种方式：

**质量监控自动触发**：每次 SelfCritic 完成评估，分数上报给 `QualityMonitor`。它追踪最近 N 次评分的滚动平均值，当均值持续低于阈值时，自动触发演进流程。这不是单次低分就触发（避免噪音），而是趋势性下滑才触发。

**手动触发**：用户主动要求进行一次演进评估。

触发后，演进循环自动执行：运行完整 Eval → 分析失败用例 → 生成候选 Prompt → A/B 测试 → 人工确认（可配置跳过）→ 采纳或拒绝 → 记录到演进日志。

整个过程有几个安全边界是必须的，不是可选的：

```python
MAX_EVOLUTION_PER_DAY    = 1     # 每天最多演进一次
MAX_PROMPT_CHANGE_RATIO  = 0.4   # 新旧 Prompt 差异不超过 40%
MIN_IMPROVEMENT_THRESHOLD = 0.3  # A/B 测试至少提升 0.3 分才采纳
ROLLBACK_SCORE_DROP      = 1.0   # 新版本比旧版本低超过 1 分自动回滚
```

这些边界背后是一个重要的认知：**自我改进系统最大的风险是失控，不是改进太慢**。一个每天改进一次、有明确验证机制、可以随时回滚的系统，远比一个快速但不稳定的演进系统更可靠。

## 六、踩坑实录

**坑 1：LLM 制定的计划里步骤间有隐性依赖**

Planner 生成了两个标为「无依赖可并行」的研究步骤，但实际上第二步需要用到第一步的结论来确定搜索方向。并行执行导致第二步产出了完全不相关的内容。

修复：在 Planner 的 system prompt 里加强对依赖关系的定义——要求 LLM 显式说明「这两步是否完全独立，各自不需要对方的任何信息」。不只是问「有没有依赖」，而是问更具体的问题。

**坑 2：SelfCritic 给自己的错误输出打了高分**

一个步骤的输出在事实上是错误的（搜索到了过时信息），但 SelfCritic 评了 8 分——因为「格式规范、逻辑清晰、覆盖了里程碑要求的条目数量」。

修复：在 Critic 的 system prompt 里把「事实准确性」作为独立维度单独评分，且设为否决项——事实错误不论其他维度多高，综合分不能超过 5 分。

**坑 3：动态重规划后的步骤 ID 和已有步骤冲突**

重规划时新生成的步骤用了和已有步骤相同的 ID（比如都叫 `step-3`），导致 `depends_on` 字段的引用混乱，执行器找错了依赖。

修复：重规划生成的步骤 ID 强制加上前缀（`replan-` + uuid），和原始计划的步骤 ID 格式完全不同，从根本上避免冲突。

**坑 4：Eval 测试集被间接用于调优**

第一版实现里，PromptOptimizer 的 A/B 测试直接用了测试集里的失败用例来验证新 Prompt 效果。这导致测试集实际上参与了优化过程，通过率虚高，掩盖了真实的能力水平。

修复：严格区分测试集和开发集。优化器拿测试集的失败用例做分析，但 A/B 测试用专门维护的开发集（不和测试集重叠）。测试集只在「想知道真实表现如何」时运行，不参与任何优化过程。

**坑 5：演进循环在质量本来就很差时陷入无效循环**

当 Agent 的基础质量很差（大量用例不通过），演进循环反复触发，每次都生成新 Prompt，但因为根本问题不在 Prompt（而在工具质量或模型能力边界），每次改进都不显著，循环一直不停止。

修复：加入连续失败保护——如果连续三次演进都没有达到 `MIN_IMPROVEMENT_THRESHOLD`，自动停止演进循环，并记录「需要人工介入」的状态。不是所有问题都能通过 Prompt 自动优化解决。

## 七、Goodhart's Law 与自我演进的边界

这是 P5 里最需要诚实讨论的部分。

Goodhart's Law：**当一个测量指标变成目标时，它就不再是一个好的测量指标。**

在 AI 自我改进系统里，这条定律特别危险：如果演进循环的目标是「让 Eval 得分更高」，系统最终会学会「在 Eval 题目上表现好」，而不是「真正对用户有帮助」。这两者一开始几乎等价，但随着优化轮次增加，差距会越来越大。

我们的实现用了三种措施来缓解（注意是缓解，不是解决）：

测试集和开发集严格分离，优化过程接触不到测试集；每次显著变更需要 Human Review，人类直觉能发现「这个 Prompt 看起来是在针对考题」；每日演进上限，给人类足够时间观察真实效果。

但这些措施只能减缓 Goodhart's Law 的影响，不能消除它。真正的解决方案是：Eval 用例必须尽可能反映真实使用场景，而不是理想化的测试情景。用户真实提出的、多样的、有时候模糊的问题，比精心设计的测试用例更能反映 Agent 的真实能力。

定期把一批真实用户对话（脱敏后）加入 Eval 测试集，是让评估持续有效的最重要的工程实践。

## 八、P5 阶段全部产出

经过这个阶段，Mnemis 第一次具备了「自我意识」——能评估自己，能从经验中学习，能在没有人告诉它的情况下主动改进：

- **`core/planning/models.py`**：`PlanStep` / `ExecutionPlan` / `StepStatus`（含 REPLANNING 状态）
- **`core/planning/planner.py`**：`GoalPlanner`，含初始规划和动态重规划
- **`core/planning/executor.py`**：`PlanExecutor`，含并行执行、反思集成、演进上报
- **`core/planning/reflection.py`**：`SelfCritic` + `ReflectionMemoryWriter`，三层反思
- **`core/eval/models.py`**：五维度评估数据结构
- **`core/eval/cases.py`**：20 个标准测试用例
- **`core/eval/runner.py`**：`EvalRunner`，LLM-as-Judge + SQLite 持久化
- **`core/eval/reporter.py`**：`EvalReporter`，历史趋势对比
- **`core/eval/prompt_manager.py`**：`PromptManager`，版本管理 + 回滚
- **`core/eval/optimizer.py`**：`PromptOptimizer`，失败分析 + A/B 测试
- **`core/planning/evolution.py`**：`QualityMonitor` + `EvolutionLoop`，完整自我改进闭环

核心认知：自我改进不是让 Agent 变得「更聪明」，而是让它在特定的任务域里变得「更可靠」。区别在于：前者是模型能力的提升（需要重新训练），后者是行为策略的优化（通过 Prompt 工程和经验积累实现）。我们做的是后者，要清醒地知道这件事的边界在哪里。
